## 1. Problem Statement

Деловой пользователь (предприниматель, аналитик, топ-менеджер) тратит ~2,5 ч/день на ручной обход 10+ новостных источников. 70–130 сообщений в день, 80% — шум и дубли. Существующие решения либо корпоративные и дорогие (Медиалогия, СКАН), либо ручные (Telegram-каналы + ChatGPT). Промежуточного слоя — персонального агента, который понимает запрос на естественном языке и возвращает релевантные материалы из заранее доверенных источников — нет.

**Применительно к Step 0:** прежде чем строить доставку, расписание, UI и тарифы, нужно ответить на единственный технический вопрос:

> Сможем ли мы по NL-запросу пользователя автоматически отобрать релевантные свежие материалы из 3–5 ключевых российских деловых источников с качеством, которое команда считает «достаточным» по согласованным метрикам (§8, §9)?

Если ответ «нет» — нет смысла строить остальное. Step 0 — это **проверка ядра**, не продукт для конечного пользователя.

## 3. Core User Stories (Given/When/Then)

### Story 1 — Запуск брифинга одной командой (CLI only)

**As a** разработчик команды,
**I want** запустить брифинг одной командой с NL-запросом,
**so that** проверить пайплайн без необходимости разбираться в инфраструктуре.

**Acceptance Criteria:**
- **Given** установлены зависимости (`uv sync`), **When** я выполняю `uv run newscore "курс валют"`, **Then** в stdout появляется валидный JSON со списком материалов и процесс завершается с exit code 0.
- **Given** запрос пустой (`""`), **When** запускаю команду, **Then** возвращается ошибка с понятным сообщением (`{"error": "query is empty"}`, exit code != 0).

> **Решение по scope:** HTTP-эндпоинт **не входит в Step 0**. Только CLI. Веб-сервис появляется на Step 2 (доставка) — см. roadmap.

---

### Story 2 — Конфиг источников

**As a** разработчик команды,
**I want** держать список источников в конфигурационном файле,
**so that** добавлять/убирать источники без правки кода.

**Acceptance Criteria:**
- **Given** есть `configs/sources.yaml`, **When** я добавляю новый источник с полями `{name, rss_url, body_extractor}`, **Then** при следующем запуске брифинга он участвует в сборе без правки Python-кода.
- **Given** в конфиге описан невалидный источник (битый URL, неверный формат), **When** запускается брифинг, **Then** ошибка по конкретному источнику логируется, но остальные источники продолжают работу.
- **Given** конфиг пуст, **When** запускается брифинг, **Then** возвращается осмысленная ошибка (`"no sources configured"`).

---

### Story 3 — Парсинг N источников

**As a** разработчик команды,
**I want** парсер, который собирает свежие материалы по 3–5 источникам,
**so that** иметь корпус для матчинга по каждому запросу.

**Acceptance Criteria:**
- **Given** в конфиге 3–5 источников с RSS-фидами, **When** запускается этап парсинга, **Then** для каждого источника собираются материалы за окно свежести (по умолчанию 7 дней), извлекается `{title, url, source, published_at, snippet, body?}`.
- **Given** для материала доступно тело статьи через `trafilatura` по URL, **When** парсер обработал статью, **Then** поле `body` содержит чистый текст без HTML-разметки и шума.
- **Given** один из источников вернул HTTP 5xx / таймаут / битый XML, **When** идёт сбор, **Then** ошибка логируется, источник пропускается, остальные продолжают работу, в финальном output есть метаполе `partial: true` с указанием упавших источников.
- **Given** материал старше окна свежести, **When** парсер его встречает, **Then** материал отбрасывается до этапа матчинга (фильтрация по `published_at`).

---

### Story 4 — Матчер: релевантные материалы

**As a** тех. лид / разработчик,
**I want** чтобы матчер возвращал топ-N материалов, релевантных запросу,
**so that** оценить, годится ли подход для briefing-first.

**Acceptance Criteria:**
- **Given** есть корпус собранных материалов и NL-запрос, **When** работает матчер, **Then** возвращается список из не более чем N материалов (N в конфиге, дефолт 10), отсортированных по убыванию оценки релевантности.
- **Given** в корпусе нет ни одного релевантного материала по выбранной метрике, **When** работает матчер, **Then** возвращается пустой список + метаполе `reason: "no_relevant_matches"` (не ошибка, валидный пустой ответ).
- **Given** матчер — embedding-based (`intfloat/multilingual-e5-base`), **When** запускается на одном и том же корпусе и запросе, **Then** результат детерминирован (модель в режиме `eval`, без random sampling).
- **Given** реализован интерфейс `Matcher` с подключаемыми реализациями, **When** добавляется второй матчер (BM25 — в Should), **Then** переключение между матчерами — флаг CLI `--matcher=embedding|bm25`.

> **Решение по scope:**
> - **Must:** один матчер — **embedding-based** (`intfloat/multilingual-e5-base`, локально, без API). Обоснование: детерминирован, работает на коротких NL-запросах, не упирается в rate limits/ключи.
> - **Should:** BM25 как дешёвый baseline для side-by-side сравнения на эталонных запросах.
> - **Could:** LLM-as-judge (только если первые два не вытягивают согласованный DoD — см. §8/§9).

---

### Story 5 — Логи каждого шага

**As a** разработчик / тех. лид,
**I want** видеть в логах, что произошло на каждом шаге пайплайна,
**so that** при «странном» результате понять, на каком этапе что-то пошло не так.

**Acceptance Criteria:**
- **Given** запущен брифинг, **When** проходит каждый этап пайплайна (парсинг, извлечение тела, матчинг), **Then** в stderr пишется структурированный лог: `{step, source, items_in, items_out, duration_ms, errors[]}`.
- **Given** материал был отброшен матчером, **When** включён уровень `DEBUG`, **Then** в логе видно score материала и причину отброса (ниже порога / не вошёл в топ-N).
- **Given** запускается с флагом `--trace`, **When** брифинг завершён, **Then** в отдельном файле `traces/<run_id>.json` сохраняется полный trace.

---

### Story 6 — Качественный тест на эталонных запросах

**As a** тех. лид / член команды,
**I want** прогнать пайплайн на 5–7 эталонных запросах и сравнить с ожидаемым множеством материалов,
**so that** иметь измеримый ответ «качество достаточное / нет».

**Acceptance Criteria:**
- **Given** до старта прогона команда составила «ожидаемые» множества материалов для 7 эталонных запросов (`курс валют`, `ставка ЦБ`, `санкции против РФ`, `IT-импортозамещение`, `сделки M&A в финтехе`, `автоваз`, длинный сложный запрос про M&A Сбер+ВТБ), **When** запускается прогон, **Then** для каждого запроса сохраняется output и сравнивается с ожиданием.
- **Given** прогон завершён, **When** команда смотрит результат, **Then** для каждого запроса фиксируется в таблице: `{query, expected_count, returned_count, overlap, precision@10, cap_precision, qualitative_verdict}`.
- **Given** на минимум **4 из 7 непустых эталонных запросов** cap_precision ≥ 0.5 (см. §9 — обновлённый DoD), **Then** Step 0 считается пройденным. Иначе — пересматриваем матчер / источники / окно свежести.

---

### Story 7 — README для запуска

**As a** проверяющий (член команды / комиссия защиты / новый контрибьютор),
**I want** запустить пайплайн у себя на ноутбуке за 5 минут после `git clone`,
**so that** проверить результат не привлекая основного разработчика.

**Acceptance Criteria:**
- **Given** свежий `git clone` репозитория, **When** я выполняю шаги из README, **Then** через ≤ 5 команд (включая установку зависимостей) получаю работающий брифинг по тестовому запросу.
- **Given** README, **When** читаю его, **Then** вижу: (1) системные требования (Python ≥ 3.11, OS), (2) команду установки, (3) команду запуска, (4) пример output JSON, (5) пояснение про cold start embedding-модели (~3 минуты при первом прогоне).
- **Given** не указаны секреты, **When** запускается брифинг, **Then** возвращается понятная ошибка с указанием, какую переменную окружения добавить (в Step 0 секретов нет — embedding локальный).

## 4. MoSCoW Feature List

### Must have (без этого Step 0 не закрывается)

- **CLI-команда** для запуска брифинга по NL-запросу. HTTP-эндпоинт — out of scope Step 0.
- Конфиг 5 источников (зафиксировано в `sources-research.md`): РБК main / Коммерсантъ / Ведомости business / Интерфакс / Forbes Russia.
- RSS-парсинг + **источник-специфичные экстракторы тела**:
  - `rbc_native` — берёт полный текст из RSS-namespace `<rbc_news:full-text>` (без сетевого вызова).
  - `trafilatura` (fallback) — HTTP GET по `<link>` + извлечение текста для остальных.
- Окно свежести (по умолчанию 7 дней, переопределяется параметром).
- **Один матчер: embedding-based** (`intfloat/multilingual-e5-base`, локально, детерминированный).
- Базовая дедупликация **по URL** (один URL — одна карточка).
- Output JSON с полями `{title, url, source, published_at, snippet, score}` для каждого материала.
- Структурированные логи каждого шага.
- Graceful degradation при падении одного из источников (метаполе `partial: true`).
- README с инструкцией запуска.
- Эталонные запросы (5–7) с заранее составленным ожидаемым множеством материалов.
- Qualitative report по итогам прогона на эталонных запросах.

### Should have (желательно, но не блокирует DoD)

- **BM25-матчер** как дешёвый baseline для side-by-side сравнения с embedding-матчером (флаг `--matcher=bm25`). Сравнение на эталонных запросах — материал для решения, какой матчер брать в Step 1.
- Локальный кэш скачанных статей (файлы на диск) — повторный прогон того же набора источников не качает заново.
- Trace-файл (`--trace`) с пошаговым выводом для разбора кейсов.
- Дедупликация по хэшу `title + link` (поверх URL-дедупликации).

### Could have (если останется время, не цель Step 0)

- LLM-judge матчер (только если embedding + BM25 не вытягивают согласованный DoD).
- Параллельный сбор источников (asyncio / threading) — реализовано, см. ADR-12..17.
- Конфигурируемый формат output (JSON / JSONL / CSV).
- Базовая семантическая дедупликация (cosine similarity заголовков).

### Won't have в Step 0 (намеренно вынесено в roadmap)

> Эти пункты **есть** в концепции / целевом продукте, но **выкинуты** из Step 0 по решению команды (на основе фидбека Димы Гальченко 18.05.2026). Не значит «никогда» — значит «не сейчас». См. `roadmap.md`.

- **UI / веб-интерфейс** — Step 5 (продуктивизация).
- **Доставка (email, Telegram, web-страница)** — Step 2.
- **Фоновый мониторинг тем / планировщик / cron** — Step 1.
- **Концепт «темы» с persistent state, дельты «новое со вчера»** — Step 1.
- **Суммаризация (ruT5 / YandexGPT / LLM)** — Step 3.
- **NER / классификация / 5 категорий контента** — Step 3.
- **Importance scoring, ranking по свежести × источник × NER** — Step 3.
- **Семантическая дедупликация одного события из разных источников (MinHash+LSH, эмбеддинги тел)** — Step 3 (кроме базовой по URL — она в Should).
- **NLI-проверка фактов** — Step 3.
- **Регистрация / аккаунты / тарифы / платежи** — Step 5.
- **БД (PostgreSQL, миграции)** — для Step 0 хватает in-memory + файлового кэша. SQLite — Step 1.
- **Деплой (Yandex Cloud, Docker prod)** — Step 5.
- **Расширение базы источников до 15+** — Step 4.
- **Открытый веб-краулинг, robots.txt-инфраструктура** — Step 4.
- **B2B-интеграция с ЕРА** — Step 5.
- **Multi-tenant, авторизация, persistent сессии** — Step 5.

## 5. Non-Functional Requirements

### Performance

- Полный брифинг (3–5 источников, окно 7 дней, матчер выбран) выполняется **за порядок десятков секунд** на типичном dev-ноутбуке. Фактически измерено: BM25 ~22с, embedding ~36с (после внедрения async fetch, см. ADR-12..17).
- **Жёсткий потолок:** 2 минуты на запрос. Сейчас оба матчера в пределах потолка.
- Для LLM-judge матчера допустимо превышение до 3–5 минут (платим за гибкость) — но фиксируется в README как известное ограничение.

### Воспроизводимость

- Один и тот же запрос на **зафиксированном корпусе** (snapshot) даёт **одинаковый output** при последовательных запусках.
- Для BM25 и embedding — детерминированно (никакого случайного семплинга).
- Для LLM-judge — фиксируем `temperature=0` и сохраняем модель/версию в output.
- Output JSON содержит метаполе `run_id`, `matcher_version`, `sources_snapshot_at`.

### Наблюдаемость

- Структурированные логи (`structlog`, JSON или console renderer).
- Минимум события: start/end каждого этапа, число материалов на входе/выходе, длительность, ошибки источников.
- Trace-режим (опциональный): полный дамп пайплайна в `traces/<run_id>.json`.
- **Что НЕ требуется:** Prometheus, Grafana, ELK, distributed tracing — это для Step 5.

### Запускаемость на dev-машинах команды

- **Поддерживаемые ОС:** macOS (M-серия, Intel) + Linux x86_64. Тестируется команда.
- **Python:** ≥ 3.11.
- **Windows:** best effort, не блокирующее.
- **Зависимости:** минимизированы. Embedding модель ~280 МБ скачивается один раз в HF cache.
- Установка одной командой (`uv sync`).

### НЕ требуется на Step 0

- Security hardening (auth, RBAC, secrets vault).
- Multi-tenant.
- High availability, failover, репликация.
- Observability stack (Prometheus / Grafana / OpenTelemetry).
- Prod-grade БД (PostgreSQL, миграции).
- Rate limiting, robots.txt-движок (Step 4).
- CI/CD pipeline.

## 6. Edge Cases

Отобраны из `mvp-pm-review.md`, отфильтрованы по применимости к Step 0 (без UI, доставки, расписания).

| # | Edge case | Поведение в Step 0 |
|---|---|---|
| 1 | **0 релевантных материалов** по запросу | Возвращается пустой массив + метаполе `reason: "no_relevant_matches"`. Не ошибка. README объясняет, как пользователь может расширить окно свежести или переформулировать. |
| 2 | **Источник упал** (5xx, таймаут, битый XML) | Источник пропускается, ошибка логируется. В output добавляется `partial: true` + `failed_sources: [...]`. Exit code = 0 (частичный результат лучше пустого). |
| 3 | **Все источники упали** | Output — пустой массив, `partial: true`, `failed_sources` = все. Exit code = 1 (отличаем от case 1). |
| 4 | **Бессмысленный / токсичный / англоязычный запрос** | Step 0: запрос идёт в матчер as-is. Если матчер ничего не нашёл — case 1. **Никакой валидации запроса** до матчинга в Step 0 нет. |
| 5 | **Очень короткий запрос** (1–2 слова) | Идёт в матчер as-is. BM25 на коротком запросе работает хуже — это известное ограничение (см. baseline). |
| 6 | **Очень длинный запрос** (20+ слов) | Идёт в матчер as-is. Embedding обрезается по токен-лимиту модели (≤ 512 токенов). LLM-judge — по контекстному окну. Логируется. |
| 7 | **Дубликаты одного события из разных источников** | **Базовая дедупликация по URL — Must.** Семантическая дедупликация — Won't (Step 3). В Step 0 пользователь **может увидеть 2–3 карточки про одно и то же событие** — known limitation. |
| 8 | **Галлюцинации матчера** (если выбран LLM-judge) | В Step 0 — никакой проверки. LLM возвращает score и обоснование, оба пишутся в log/trace. |
| 9 | **Пейволлы (Ведомости, Forbes Russia)** | Если `trafilatura` не смог извлечь тело — материал остаётся с одним RSS-снэпом (title + description). Матчер работает только по доступному тексту. Логируется флаг `body_extracted: false`. |
| 10 | **Forbes Russia блокировка / смена домена** | Проверено до старта: фид доступен (см. `sources-research.md`). Если в будущем сломается — `optional: true` в конфиге не зажигает `partial`. |
| 11 | **Дубль одинакового запроса подряд** | Step 0 не имеет persistent state брифингов. Каждый запуск — независимый. Кэш статей переиспользуется, но матчинг идёт заново. |

## 8. Success Metrics

### Quantitative — оригинальный DoD из spec

> **Обновлено в §9** — DoD на капп метрику. Этот раздел сохранён для истории.

- **% попаданий на эталонных запросах:** на минимум **4 из 7** эталонных запросов precision@10 ≥ 0.5.
- **Latency:** медианное время брифинга на эталонных запросах ≤ 60 секунд. **Фактически:** BM25 ~22с, embedding ~36с — оба укладываются.
- **Reliability сбора:** при N запусках на одних и тех же источниках ≥ 90% запусков завершаются без `partial: true`.
- **Воспроизводимость:** 100% — два последовательных запуска на одном кэше дают идентичный output.

### Qualitative

Что должна сказать команда, посмотрев результат:

- «Да, это похоже на то, что я бы сам отобрал.» — на ≥ 4 из 7 эталонных запросов.
- «Логи понятные, я вижу, что произошло на каждом шаге.» — после `--trace` прогона.
- «Я запустил это у себя по README за 10 минут.» — внешний проверяющий вне основного разработчика.
- «Это база, на которой можно строить Step 1.» — финальный вердикт по Step 0.

### Что НЕ метрика Step 0

- Количество пользователей / DAU / MAU.
- Churn, retention.
- MRR, конверсия в платных.
- NPS.
- Время до первой ценности (TTV) для конечного пользователя.

Эти метрики начинают иметь смысл с **Step 2+** (когда появляется доставка) и особенно с **Step 5** (продуктивизация). На Step 0 их преждевременное обсуждение — отвлечение.

## 9. Updates v2 (2026-05-23) — Story 6 closed, DoD pivot

После первого прогона qual-eval (см. `step0-qual-baseline.md`):

- **precision@10 из §8 не пройден формально** — embedding 2/7 ≥ 0.5, BM25 1/7 ≥ 0.5.
- **Причина — структурная**, не качество матчера: эталоны малочисленны (q01/q05 = 1 материал, q06 = 2, q07 = 0 для negative test). Потолок precision@10 для q01/q05 = 0.10, для q06 = 0.20 — физически недостижимо ≥0.5.
- **Capped precision @ min(K, |expected|)** — честная метрика на узких эталонах. Embedding: **0.89 avg** на 6 непустых, **6 из 6 ≥ 0.7**. BM25: 0.47.

### Обновлённый DoD (принят командой 2026-05-23)

- **Primary:** **capped precision** ≥ 0.5 на ≥ 4 из 6 непустых эталонных запросов.
- **Secondary:** precision@10 — индикатор «корпус достаточно богат по теме», не блокер.

**Step 0 — closed** по обновлённому DoD: embedding закрывает 6/6 непустых ≥ 0.7.

С большим отрывом от BM25 (≈2× cap_precision). LLM-judge (Could) — пока не нужен.
