# NewsCore AI — Step 0 Product Specification

> Формальная спецификация под **первый шаг** (Step 0), не под полный продукт.
> Источник scope: `docs/docs/doc-003-mvp-brief.md` (v2 после фидбека Димы Гальченко, 18.05.2026).
> Связанные доки: `doc-002-concept.md`, `doc-006-roadmap.md`, `doc-004-mvp-pm-review.md`.
> Дата: 2026-05-20.

---

## 1. Problem Statement

Деловой пользователь (предприниматель, аналитик, топ-менеджер) тратит ~2,5 ч/день на ручной обход 10+ новостных источников. 70–130 сообщений в день, 80% — шум и дубли. Существующие решения либо корпоративные и дорогие (Медиалогия, СКАН), либо ручные (Telegram-каналы + ChatGPT). Промежуточного слоя — персонального агента, который понимает запрос на естественном языке и возвращает релевантные материалы из заранее доверенных источников — нет.

**Применительно к Step 0:** прежде чем строить доставку, расписание, UI и тарифы, нужно ответить на единственный технический вопрос:

> Сможем ли мы по NL-запросу пользователя автоматически отобрать релевантные свежие материалы из 3–5 ключевых российских деловых источников с качеством, которое команда и заказчик считают «достаточным»?

Если ответ «нет» — нет смысла строить остальное. Step 0 — это **проверка ядра**, не продукт для конечного пользователя.

---

## 2. Target Users

Step 0 **не выходит к конечному пользователю**. Его аудитория:

| Роль | Что делает на Step 0 |
|---|---|
| **Заказчик (Дима Гальченко)** | Запускает скрипт у себя на машине, прогоняет эталонные запросы, оценивает релевантность глазами, принимает решение «годится / нет». |
| **Команда проекта** | Реализует пайплайн, выбирает матчер, готовит эталонные ответы для qual-теста. |
| **PM / тех. лид** | Сравнивает результаты разных матчеров, фиксирует baseline для Step 1+. |

Конечный пользователь (предприниматель / аналитик) появится со Step 2 (доставка). До этого момента продукт не имеет UX-поверхности.

## 3. Core User Stories (Given/When/Then)

### Story 1 — Запуск брифинга одной командой (CLI only)

**As a** разработчик команды,
**I want** запустить брифинг одной командой с NL-запросом,
**so that** проверить пайплайн без необходимости разбираться в инфраструктуре.

**Acceptance Criteria:**
- **Given** установлены зависимости (`pip install -r requirements.txt` или `uv sync`), **When** я выполняю `python -m newscore.briefing "курс валют"`, **Then** в stdout появляется валидный JSON со списком материалов и процесс завершается с exit code 0.
- **Given** запрос пустой (`""`), **When** запускаю команду, **Then** возвращается ошибка с понятным сообщением (`{"error": "query is empty"}`, exit code != 0).

> **Решение по scope:** HTTP-эндпоинт **не входит в Step 0**. Только CLI. Веб-сервис появляется на Step 2 (доставка) — см. roadmap.

---

### Story 2 — Конфиг источников

**As a** разработчик команды,
**I want** держать список источников в конфигурационном файле,
**so that** добавлять/убирать источники без правки кода.

**Acceptance Criteria:**
- **Given** есть `sources.yaml` (или `.toml` / `.json` — на усмотрение команды), **When** я добавляю новый источник с полями `{name, rss_url, type}`, **Then** при следующем запуске брифинга он участвует в сборе без правки Python-кода.
- **Given** в конфиге описан невалидный источник (битый URL, неверный формат), **When** запускается брифинг, **Then** ошибка по конкретному источнику логируется, но остальные источники продолжают работу.
- **Given** конфиг пуст, **When** запускается брифинг, **Then** возвращается осмысленная ошибка (`"no sources configured"`).

---

### Story 3 — Парсинг N источников

**As a** разработчик команды,
**I want** парсер, который собирает свежие материалы по 3–5 источникам,
**so that** иметь корпус для матчинга по каждому запросу.

**Acceptance Criteria:**
- **Given** в конфиге 3–5 источников с RSS-фидами, **When** запускается этап парсинга, **Then** для каждого источника собираются материалы за окно свежести (по умолчанию 7 дней), извлекается `{title, url, source, published_at, snippet, body?}`.
- **Given** для материала доступно тело статьи через `trafilatura` по URL, **When** парсер обработал статью, **Then** поле `body` содержит чистый текст без HTML-разметки и шума.
- **Given** один из источников вернул HTTP 5xx / таймаут / битый XML, **When** идёт сбор, **Then** ошибка логируется, источник пропускается, остальные продолжают работу, в финальном output есть метаполе `partial: true` с указанием упавших источников.
- **Given** материал старше окна свежести, **When** парсер его встречает, **Then** материал отбрасывается до этапа матчинга (фильтрация по `published_at`).

---

### Story 4 — Матчер: релевантные материалы

**As a** заказчик / тех. лид,
**I want** чтобы матчер возвращал топ-N материалов, релевантных запросу,
**so that** оценить, годится ли подход для briefing-first.

**Acceptance Criteria:**
- **Given** есть корпус собранных материалов и NL-запрос, **When** работает матчер, **Then** возвращается список из не более чем N материалов (N в конфиге, дефолт 10), отсортированных по убыванию оценки релевантности.
- **Given** в корпусе нет ни одного релевантного материала по выбранной метрике, **When** работает матчер, **Then** возвращается пустой список + метаполе `reason: "no_relevant_matches"` (не ошибка, валидный пустой ответ).
- **Given** матчер — embedding-based (`intfloat/multilingual-e5-base`), **When** запускается на одном и том же корпусе и запросе, **Then** результат детерминирован (модель в режиме `eval`, без random sampling).
- **Given** реализован интерфейс `Matcher` с подключаемыми реализациями, **When** добавляется второй матчер (BM25 — в Should), **Then** переключение между матчерами — флаг CLI `--matcher=embedding|bm25`.

> **Решение по scope:**
> - **Must:** один матчер — **embedding-based** (`intfloat/multilingual-e5-base`, локально, без API). Обоснование: детерминирован, работает на коротких NL-запросах, не упирается в rate limits/ключи.
> - **Should:** BM25 как дешёвый baseline для side-by-side сравнения на эталонных запросах.
> - **Could:** LLM-as-judge (только если первые два не вытягивают precision@10 ≥ 0.5 на эталонных).

---

### Story 5 — Логи каждого шага

**As a** разработчик / заказчик,
**I want** видеть в логах, что произошло на каждом шаге пайплайна,
**so that** при «странном» результате понять, на каком этапе что-то пошло не так.

**Acceptance Criteria:**
- **Given** запущен брифинг, **When** проходит каждый этап пайплайна (парсинг, извлечение тела, матчинг), **Then** в stderr (или файл `briefing.log`) пишется структурированный лог: `{step, source, items_in, items_out, duration_ms, errors[]}`.
- **Given** материал был отброшен матчером, **When** включён уровень `DEBUG`, **Then** в логе видно score материала и причину отброса (ниже порога / не вошёл в топ-N).
- **Given** запускается с флагом `--trace`, **When** брифинг завершён, **Then** в отдельном файле `traces/<run_id>.json` сохраняется полный trace: какие источники опрошены, сколько материалов собрано на каждом, что попало в топ-N и почему.

---

### Story 6 — Качественный тест на эталонных запросах

**As a** PM / тех. лид,
**I want** прогнать пайплайн на 5–7 эталонных запросах и сравнить с ожидаемым множеством материалов,
**so that** иметь измеримый ответ «качество достаточное / нет».

**Acceptance Criteria:**
- **Given** до старта кодинга команда составила «ожидаемые» множества материалов для 5–7 эталонных запросов (`курс валют`, `ставка ЦБ`, `санкции против РФ`, `IT-импортозамещение`, `сделки M&A в финтехе`, `автоваз`, длинный сложный запрос про M&A Сбер+ВТБ), **When** запускается прогон, **Then** для каждого запроса сохраняется output и сравнивается с ожиданием.
- **Given** прогон завершён, **When** PM / Дима смотрят результат, **Then** для каждого запроса фиксируется в таблице: `{query, expected_count, returned_count, overlap, precision@10, qualitative_verdict}`.
- **Given** на минимум 4 из 7 эталонных запросов qualitative_verdict = «релевантно», **Then** Step 0 считается пройденным. Иначе — пересматриваем матчер / источники / окно свежести.

---

### Story 7 — README для запуска

**As a** заказчик (Дима),
**I want** запустить пайплайн у себя на ноутбуке за 5 минут после `git clone`,
**so that** проверить результат не привлекая команду.

**Acceptance Criteria:**
- **Given** свежий `git clone` репозитория, **When** я выполняю шаги из README, **Then** через ≤ 5 команд (включая установку зависимостей) получаю работающий брифинг по тестовому запросу.
- **Given** README, **When** читаю его, **Then** вижу: (1) системные требования (Python ≥ 3.11, OS), (2) команду установки, (3) команду запуска, (4) пример output JSON, (5) скриншот или вывод логов.
- **Given** не указаны секреты (ключи LLM-провайдера, если матчер = LLM-judge), **When** запускается брифинг, **Then** возвращается понятная ошибка с указанием, какую переменную окружения добавить.

## 4. MoSCoW Feature List

### Must have (без этого Step 0 не закрывается)

- **CLI-команда** для запуска брифинга по NL-запросу. HTTP-эндпоинт — out of scope Step 0.
- Конфиг 5 источников (зафиксировано в `sources-research.md`): РБК main / Коммерсантъ / Ведомости business / Интерфакс / Forbes Russia.
- RSS-парсинг + **источник-специфичные экстракторы тела**:
  - `rbc_native` — берёт полный текст из RSS-namespace `<rbc_news:full-text>` (без сетевого вызова).
  - `trafilatura` (fallback) — HTTP GET по `<link>` + извлечение текста для остальных.
- Окно свежести (по умолчанию 7 дней, переопределяется параметром).
- **Один матчер: embedding-based** (`intfloat/multilingual-e5-base`, локально, детерминированный).
- Базовая дедупликация **по URL** (один URL — одна карточка).
- Output JSON с полями `{title, url, source, published_at, snippet, score}` для каждого материала.
- Структурированные логи каждого шага.
- Graceful degradation при падении одного из источников (метаполе `partial: true`).
- README с инструкцией запуска.
- Эталонные запросы (5–7) с заранее составленным ожидаемым множеством материалов.
- Qualitative report по итогам прогона на эталонных запросах.

### Should have (желательно, но не блокирует DoD)

- **BM25-матчер** как дешёвый baseline для side-by-side сравнения с embedding-матчером (флаг `--matcher=bm25`). Сравнение на эталонных запросах — материал для решения, какой матчер брать в Step 1.
- Локальный кэш скачанных статей (файлы на диск) — повторный прогон того же набора источников не качает заново.
- Trace-файл (`--trace`) с пошаговым выводом для разбора кейсов.
- Дедупликация по хэшу `title + link` (поверх URL-дедупликации).

### Could have (если останется время, не цель Step 0)

- LLM-judge матчер (только если embedding + BM25 не вытягивают precision@10 ≥ 0.5 на эталонных).
- Параллельный сбор источников (asyncio / threading) — ускорение, но не критично.
- Конфигурируемый формат output (JSON / JSONL / CSV).
- Базовая семантическая дедупликация (cosine similarity заголовков).

### Won't have в Step 0 (намеренно вынесено в roadmap)

> Эти пункты **есть** в концепции / целевом продукте, но **выкинуты** из Step 0 по решению заказчика. Не значит «никогда» — значит «не сейчас». См. `doc-006-roadmap.md`.

- **UI / веб-интерфейс** — Step 5 (продуктивизация).
- **Доставка (email, Telegram, web-страница)** — Step 2.
- **Фоновый мониторинг тем / планировщик / cron** — Step 1.
- **Концепт «темы» с persistent state, дельты «новое со вчера»** — Step 1.
- **Суммаризация (ruT5 / YandexGPT / LLM)** — Step 3.
- **NER / классификация / 5 категорий контента** — Step 3.
- **Importance scoring, ranking по свежести × источник × NER** — Step 3.
- **Семантическая дедупликация одного события из разных источников (MinHash+LSH, эмбеддинги тел)** — Step 3 (кроме базовой по URL — она в Should).
- **NLI-проверка фактов** — Step 3.
- **Регистрация / аккаунты / тарифы / платежи** — Step 5.
- **БД (PostgreSQL, миграции) — для Step 0 хватает in-memory + файлового кэша**. SQLite — Step 1.
- **Деплой (Yandex Cloud, Docker prod)** — Step 5.
- **Расширение базы источников до 15+** — Step 4.
- **Открытый веб-краулинг, robots.txt-инфраструктура** — Step 4.
- **B2B-интеграция с ЕРА** — Step 5.
- **Multi-tenant, авторизация, persistent сессии** — Step 5.

## 5. Non-Functional Requirements

### Performance

- Полный брифинг (3–5 источников, окно 7 дней, матчер выбран) выполняется **за порядок десятков секунд** на типичном dev-ноутбуке (M-серия Mac / современный Linux ноут). Это не SLA для prod — это пограничное значение, при котором итерация удобна для разработчика.
- **Жёсткий потолок:** 2 минуты на запрос. Если выходит за это — оптимизируем (параллельный сбор, кэш, выбор более лёгкого матчера).
- Для LLM-judge матчера допустимо превышение до 3–5 минут (платим за гибкость) — но фиксируется в README как известное ограничение.

### Воспроизводимость

- Один и тот же запрос на **зафиксированном корпусе** (закэшированные статьи) даёт **одинаковый output** при последовательных запусках.
- Для BM25 и embedding — детерминированно (никакого случайного семплинга).
- Для LLM-judge — фиксируем `temperature=0` (или эквивалент в провайдере) и сохраняем модель/версию в output для трассировки.
- Output JSON содержит метаполе `run_id`, `matcher_version`, `sources_snapshot_at`.

### Наблюдаемость

- Структурированные логи (JSON-lines в stderr / в `briefing.log`).
- Минимум события: start/end каждого этапа, число материалов на входе/выходе каждого этапа, длительность, ошибки источников.
- Trace-режим (опциональный): полный дамп пайплайна в `traces/<run_id>.json`.
- **Что НЕ требуется:** Prometheus, Grafana, ELK, distributed tracing — это для Step 5.

### Запускаемость на dev-машинах команды

- **Поддерживаемые ОС:** macOS (M-серия, Intel) + Linux x86_64. Тестируется командой и Димой.
- **Python:** ≥ 3.11.
- **Windows:** best effort, не блокирующее. Если на защите/демо нужен Windows — заранее проверяем; иначе считаем «under question» и в README указываем «not officially supported in Step 0».
- **Зависимости:** минимизированы. Если матчер = embedding с локальной моделью — добавляем `torch` + `sentence-transformers`, но фиксируем размер и время cold start в README.
- Установка одной командой (`pip install -r requirements.txt` или `uv sync`).

### НЕ требуется на Step 0

- Security hardening (auth, RBAC, secrets vault — есть только `.env`).
- Multi-tenant.
- High availability, failover, репликация.
- Observability stack (Prometheus / Grafana / OpenTelemetry).
- Prod-grade БД (PostgreSQL, миграции).
- Rate limiting, robots.txt-движок (Step 4).
- CI/CD pipeline (минимум — линтер + тест локально, GitHub Actions опционально).
- Performance benchmarks как формальная процедура — достаточно eyeball-замера.

## 6. Edge Cases

Отобраны из `doc-004-mvp-pm-review.md`, отфильтрованы по применимости к Step 0 (без UI, доставки, расписания).

| # | Edge case | Поведение в Step 0 |
|---|---|---|
| 1 | **0 релевантных материалов** по запросу | Возвращается пустой массив + метаполе `reason: "no_relevant_matches"`. Не ошибка. README объясняет, как пользователь может расширить окно свежести или переформулировать. |
| 2 | **Источник упал** (5xx, таймаут, битый XML) | Источник пропускается, ошибка логируется. В output добавляется `partial: true` + `failed_sources: [...]`. Exit code = 0 (частичный результат лучше пустого). |
| 3 | **Все источники упали** | Output — пустой массив, `partial: true`, `failed_sources` = все. Exit code = 1 (отличаем от case 1). |
| 4 | **Бессмысленный / токсичный / англоязычный запрос** | Step 0: запрос идёт в матчер as-is. Если матчер ничего не нашёл — case 1. **Никакой валидации запроса** до матчинга в Step 0 нет (это Step 5). Это явный edge case, ожидаемое поведение — пустой результат, не ошибка. |
| 5 | **Очень короткий запрос** (1–2 слова) | Идёт в матчер as-is. BM25 на коротком запросе работает хуже — это известное ограничение, фиксируется в qual-тесте. Если результат «плохо» — это сигнал для выбора другого матчера. |
| 6 | **Очень длинный запрос** (20+ слов, как в эталоне №7) | Идёт в матчер as-is. BM25 — стемминг + стопслова. Embedding — обрезается по токен-лимиту модели (≤ 512 токенов). LLM-judge — обрезается по контекстному окну. Логируется, если применилась обрезка. |
| 7 | **Дубликаты одного события из разных источников** (одна и та же новость на РБК и Коммерсантъ) | **Базовая дедупликация по URL — Must.** Семантическая дедупликация — Won't (Step 3). Значит в Step 0 пользователь **может увидеть 2–3 карточки про одно и то же событие** — это known limitation, фиксируем в README. |
| 8 | **Галлюцинации матчера** (если выбран LLM-judge) | В Step 0 — никакой проверки. LLM возвращает score и обоснование, оба пишутся в log/trace. Если глазами видно, что обоснование «галлюцинирует» — фиксируется в qual-report как минус LLM-judge. Это материал для решения «какой матчер берём дальше». |
| 9 | **Пейволлы (Ведомости, Forbes Russia)** | Если `trafilatura` не смог извлечь тело — материал остаётся с одним RSS-снэпом (title + description). Матчер работает только по доступному тексту. Логируется флаг `body_extracted: false`. |
| 10 | **Forbes Russia блокировка / смена домена** | Проверяется до старта кодинга (см. Open Q1). Если недоступен из РФ без VPN — исключается из списка источников или помечается `optional: true`. |
| 11 | **Дубль одинакового запроса подряд** | Step 0 не имеет persistent state брифингов. Каждый запуск — независимый. Кэш статей переиспользуется, но матчинг идёт заново. Это ОК на Step 0 (proper кэширование результата — Step 1). |

## 8. Success Metrics

### Quantitative

- **% попаданий на эталонных запросах:** на минимум **4 из 7** эталонных запросов precision@10 ≥ 0.5 (минимум 5 из топ-10 материалов команда оценивает как релевантные).
- **Latency:** медианное время брифинга на эталонных запросах ≤ 60 секунд (BM25/embedding), ≤ 3 минут (LLM-judge). Если хуже — звонок про оптимизацию.
- **Reliability сбора:** при N запусках на одних и тех же источниках ≥ 90% запусков завершаются без `partial: true` (источники стабильно отдают данные). Если ниже — пересматриваем список источников.
- **Воспроизводимость:** 100% — два последовательных запуска на одном кэше дают идентичный output (модуль temperature LLM-judge).

### Qualitative

Что должен сказать Дима / заказчик, посмотрев результат:

- «Да, это похоже на то, что я бы сам отобрал.» — на ≥ 4 из 7 эталонных запросов.
- «Логи понятные, я вижу, что произошло на каждом шаге.» — после `--trace` прогона.
- «Я запустил это у себя по README за 10 минут.» — Дима/команда вне основного разработчика.
- «Это база, на которой можно строить Step 1.» — финальный вердикт по Step 0.

### Что НЕ метрика Step 0

- Количество пользователей / DAU / MAU.
- Churn, retention.
- MRR, конверсия в платных.
- NPS.
- Время до первой ценности (TTV) для конечного пользователя.

Эти метрики начинают иметь смысл с **Step 2+** (когда появляется доставка) и особенно с **Step 5** (продуктивизация). На Step 0 их преждевременное обсуждение — отвлечение.

## Next Steps

- **RECOMMEND: architect** — спроектировать минимальную архитектуру под этот spec: модуль `parser`, модуль `matcher` (с интерфейсом для подмены реализации), модуль `runner` (CLI + HTTP), формат конфига, формат trace, layout репозитория.
- **RECOMMEND: security** — **не требуется на Step 0**. Persistent state, секреты пользователей, платежи, auth — всё это Step 5. Единственная потенциальная security-задача — обработка ключей LLM-провайдера через `.env` / `os.environ`, тривиально.
- **OPEN QUESTIONS** (блокируют начало кодинга, см. Section 7): итоговый список источников; RSS+trafilatura vs RSS-only; число матчеров; LLM-провайдер; роли и сроки; ответственный за «ожидаемые» множества; стратегия дедупликации.
- **RISK FLAGS:**
  - **R1.** Forbes Russia / Ведомости могут оказаться частично недоступны (блокировка / пейволл). Mitigation: техресёрч 1 час до старта, при необходимости — замена.
  - **R2.** BM25 на коротких запросах («курс валют», 2 слова) даёт плохое качество. Mitigation: иметь второй матчер (embedding или LLM-judge) для сравнения. Решение по «победителю» — после qual-теста.
  - **R3.** LLM-judge упирается в стоимость / rate limits провайдера, особенно если корпус большой (10 источников × 30 материалов = 300 LLM-вызовов на один брифинг). Mitigation: пред-фильтрация BM25 → топ-30 кандидатов → LLM-judge только на них.
  - **R4.** Без семантической дедупликации (намеренно out of scope) Дима / заказчик на демо может сказать «вы вернули 3 одинаковые новости». Mitigation: явно зафиксировать в README и устной презентации, что это known limitation Step 0 и решается в Step 3.
  - **R5.** Эталонные «ожидаемые» множества не подготовлены до старта кодинга → DoD не закрываем (нечем мерить). Mitigation: назначить ответственного (см. Open Q №6 в брифе) **до старта** Step 0.
