**1. ПОСТАНОВКА ЗАДАЧИ И КОНТЕКСТ**

────────────────────────────────────────────────────────────────────────────────

**1.1. Происхождение проекта**

Проект инициирован по предложению Евразийского рейтингового агентства при поддержке факультета ФТМИ Университета ИТМО. Первоначальный запрос - разработка AI-агента для парсинга и классификации новостей по категориям. В процессе уточнения концепции сформировалась идея полноценного персонализированного веб-сервиса.

Декан факультета ФТМИ и вице-президент Евразийского РА выразили заинтересованность в веб-сервисе с ежемесячной подпиской 2 000–3 000 ₽, предоставляющем персонализированные ежедневные дайджесты деловых новостей.

**1.2. Роль программного инженера**

Задача автора - обосновать техническую реализацию: выбор веб-платформы, архитектуру бэкенда, AI-пайплайн, стек технологий и инфраструктуру. Дополнительно проведён анализ целевой аудитории, рынка и конкурентов.

**2. ПРОБЛЕМА И ПРЕДЛАГАЕМОЕ РЕШЕНИЕ**

────────────────────────────────────────────────────────────────────────────────

**2.1. Боль пользователя**

Современный деловой человек ежедневно сталкивается с информационной перегрузкой:

• Десятки новостных источников (РБК, Forbes Russia, РИА Новости, Коммерсантъ, Ведомости и др.)

• Отсутствие единой точки получения релевантной информации

• 80% новостного потока - шум, кликбейт и повторы одних событий

• Нет времени вручную фильтровать и систематизировать

Ключевые цифры:

• Менеджер тратит ~2,5 ч/день на чтение новостей

• 60% деловых людей недовольны качеством существующих агрегаторов

• ~25 млн активных читателей делового контента в России

**2.2. Решение: NewsCore AI**

NewsCore AI - веб-сервис, который собирает новости из проверенных источников, очищает их от шума, суммаризирует с помощью ИИ и доставляет персонализированный дайджест.

Ключевой принцип: новости не генерируются - они берутся с реальных авторитетных сайтов, обрабатываются и представляются пользователю. Источник и ссылка на оригинал всегда сохраняются.

**5. ТЕХНОЛОГИЧЕСКИЙ СТЕК**

────────────────────────────────────────────────────────────────────────────────

**5.1. Обоснование выбора веб-платформы**

Почему веб-сервис? Веб-формат обеспечивает push-уведомления о срочных новостях, офлайн-доступ к дайджесту, нативную нотификацию по расписанию и максимальное удобство для ежедневного использования.

|  |  |  |  |
| --- | --- | --- | --- |
| **Критерий** | **Next.js** | **Nuxt.js** | **SvelteKit** |
| SSR / SSG из коробки | Да | Да | Нет |
| Скорость разработки | Высокая | Высокая | Медленно |
| Производительность | Хорошая | Отличная | Отличная |
| Экосистема / найм | Широкий рынок JS | Растущий | Узкий |
| Push / Offline поддержка | Зрелая | Зрелая | Зрелая |

Вывод: React Native - оптимальный баланс скорости разработки и качества для MVP. Поддержка Chrome, Firefox, Safari (~98% аудитории). PWA-режим для мобильных устройств.

**5.2. Backend**

Выбор Python + FastAPI обусловлен нативной интеграцией с AI/ML стеком: весь серверный код, AI-модели и инференс находятся в одной экосистеме Python. FastAPI обеспечивает async-обработку, автогенерацию OpenAPI-документации и высокую производительность.

**5.3. AI/ML компоненты**

|  |  |  |
| --- | --- | --- |
| **Компонент** | **Технология** | **Обоснование** |

**7. AI-ПАЙПЛАЙН - ЯДРО СИСТЕМЫ**

────────────────────────────────────────────────────────────────────────────────

AI-пайплайн - это место, где создаётся ключевая ценность продукта. Каждая статья проходит 7-шаговый процесс обработки в виде асинхронных задач Celery.

**7.1. Полный цикл обработки одной статьи**

|  |  |  |  |
| --- | --- | --- | --- |
| **Шаг** | **Название** | **Технология** | **Результат** |
| 1 | Парсинг | Scrapy / feedparser / Playwright | title, body, url, date → raw\_articles |
| 2 | Предобработка | trafilatura | Чистый текст без рекламы и навигации |
| 3 | Суммаризация | YandexGPT Pro API | 3–5 предложений с сохранением фактов и чисел |
| 4 | Классификация | ruBERT fine-tuned (ONNX) | Одна из 5 категорий, confidence > 0.75 |
| 5 | NER - сущности | natasha + slovnet | Организации, персоны, регионы, валюты, тикеры |
| 6 | Importance Scoring | LightGBM | Оценка 0.0–1.0 по n\_sources, recency, urgency |
| 7 | Запись в БД + кэш | PostgreSQL + Redis | processed\_articles, инвалидация кэша дайджеста |

**7.2. Метрики качества пайплайна**

|  |  |
| --- | --- |
| **Метрика** | **Целевое значение** |
| Точность классификации (ruBERT) | > 92% |
| Среднее время обработки статьи | < 8 секунд |
| Полнота суммаризации (ROUGE-L) | > 0.45 |
| Доля ложных суммаризаций | < 1% |
| Uptime парсинг-сервиса | > 99.5% |

**7.3. Дедупликация**

Одно событие часто освещается несколькими источниками. Алгоритм дедупликации:

• MinHash + LSH - нахождение похожих статей (Jaccard similarity > 0.85)

• Из группы дублей оставляется одна - наиболее полная или ранняя

• В метаданные записывается поле also\_covered\_by: [список источников]

**7.4. Расписание сбора данных**

• Каждые 15 минут - мониторинг RSS всех источников

• Каждые 30 минут - полный парсинг страниц без RSS

• 03:00 МСК - ночной батч: переобработка за прошедшие сутки, пересчёт важности

• Что добавлял в избранное

• По каким ссылкам переходил на оригинал

**8.2. Формула ранжирования**

score(article, user) = α·category\_weight + β·importance\_score + γ·recency\_score + δ·entity\_match + ε·behavioral\_score

|  |  |  |
| --- | --- | --- |
| **Коэффициент** | **Значение** | **Описание** |
| α | 0.30 | Соответствие профилю роли |
| β | 0.25 | Важность события (LightGBM score) |
| γ | 0.20 | Свежесть публикации |
| δ | 0.15 | Совпадение с watchlist компаний / персон |
| ε | 0.10 → 0.30 | Поведенческая история (растёт со временем) |
